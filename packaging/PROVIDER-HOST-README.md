# MultiVibe Host

MultiVibe Host connects your AI provider accounts through an API proxy, chat,
and account dashboard. The bundle contains the Core application, pinned Node.js,
platform launchers, the updater, and the Security module. macOS also includes
its native interface and Chromium browser panel. No local inference engine,
model weights, GPU driver, or system Node.js installation is required.

## Verify a release

Before executing a downloaded release, verify its GitHub build provenance with
an independently installed GitHub CLI:

```sh
gh attestation verify /path/to/multivibe-host_VERSION_PLATFORM_ARCHIVE \
  --repo thibautrey/multivibe
```

Do not continue if verification fails. Releases also provide signed checksums
and a Sigstore bundle. A public key downloaded with an unverified release is
not an independent trust root.

The installer checks paths, modes, sizes, and SHA-256 hashes against the release
manifest, rejects undeclared files and unsafe links, and runs `doctor`. macOS
additionally verifies application signatures and notarization. Installation is
staged and committed with a rename. `doctor` validates the bundle without
requiring an accelerator or running a model.

From a source checkout, inspect an archive with:

```sh
node scripts/provider-host/verify-provider-host.mjs /path/to/provider-host-archive
```

Add `--require-runtime` on the matching operating system and architecture to
check executable versions, Node.js/SQLite, and `doctor`.

## macOS

Open the DMG matching your Apple Silicon or Intel Mac and drag **MultiVibe
Host** into **Applications**. The disk image and app are signed and notarized.
Launch the app to open its native interface and menu bar. Provider credentials
are not placed in dashboard URLs.

Per-user installations use `~/Applications/MultiVibe Host.app`, state below
`~/Library/Application Support/MultiVibe`, and logs below
`~/Library/Logs/MultiVibe Host`. The updater uses a per-user LaunchAgent. It
checks on a randomized 10–14-hour schedule and waits for active HTTP,
WebSocket, and deferred jobs to drain before applying a verified update.
A failed health check restores the previous application.

## Linux amd64

Extract the archive and run:

```sh
./install.sh
```

The installer places the application in `~/.local/lib/multivibe-host` and
launchers in `~/.local/bin`. The native menu requires GTK 3 and a desktop
session. An available systemd user manager runs the Host and its updater;
the installer does not install or repair systemd.

Without a systemd user manager, run `./install.sh --foreground` and keep the
terminal or supervisor attached. Ctrl-C stops the foreground service.
No NVIDIA GPU is required.

## Windows amd64

Extract the ZIP and run the included `install.ps1` with PowerShell 5.1 or newer.
The application and menu run for the current user. Local credentials and
application data persist separately from the installed bundle. The updater
verifies a complete replacement and restores the previous installation if
startup fails. `uninstall.ps1` removes the installed application while
preserving data by default.

The installer retains process cleanup for older releases so an upgrade can
stop an old owned inference process. It never installs or starts that engine.

## Containers and NAS

Use the published `ghcr.io/thibautrey/multivibe-host` image or the supplied
`docker-compose.host.yml`. Persist `/data` and set `MULTIVIBE_HOST_PUBLIC_URL`
to the exact browser-facing HTTP(S) origin. GPU access and model-storage mounts
are unnecessary. Only the Core port is published; the container drops to
UID/GID 10001 and uses a read-only filesystem and restricted capabilities.
Container upgrades are managed by the container platform.

See the `packaging/unraid`, `packaging/umbrel`, and `packaging/distribution`
source documentation for their deployment packages.

## Managed company deployment

Use `--managed-profile` (`-ManagedProfilePath` on Windows) with a private,
single-target profile generated by the MultiVibe Team dashboard. See
`docs/managed-team-deployment.md`. Do not put employee API keys or instance
private keys in MDM configuration.

## Upgrade from local inference releases

Local model preparation, automatic engine discovery, capacity controls, and
machine compute sharing have been removed. Existing generated runtime accounts
are disabled on loading application state. Provider accounts and Team account
sharing continue to work.

Upgrades do not delete previously downloaded models or separate managed-runtime
directories. Those user files remain outside the application bundle and may be
removed manually after backing up anything needed. The new release does not
start their engines or download replacements.
