# Desktop Cloud accounts

The macOS chat footer opens the Cloud account picker. Adding an account uses the existing ephemeral OAuth/PKCE browser flow and verifies the identity with Cloud before exposing that account. Other accounts stay connected. Names can be edited in the account settings; removing a saved account revokes its refresh token and removes its local appearance without deleting Cloud conversations.

Credentials, account selection, the optional PIN verifier and retry limits are stored in a device-only Keychain entry. Existing single-account credentials migrate only after the replacement is saved. The Cloud journal remains keyed by account; switching immediately clears the outgoing account's in-memory conversations, runs, consent and models. Late responses cannot activate a different account. Device-owned "Sur ce Mac" conversations and Host/harness configuration retain their existing device scope; this account picker does not create separate macOS users or isolate their filesystem access.

**Ask everytime** asks for an identity at launch and after ten minutes without interaction in the MultiVibe window or its sheets. Keyboard, mouse and scrolling renew the interval. The continuous clock includes computer sleep; an interaction after expiry opens the identity picker instead of renewing the old session. An optional four-digit PIN is required whenever a protected account is unlocked, including after camera recognition or OAuth reauthorization. Its salted PBKDF2 verifier stays in Keychain, with a persisted thirty-second cooldown after five failures. Changing or removing a PIN requires the current PIN.

Camera recognition is off by default. Account settings offer five guided views of the current user's appearance. Enrollment replaces the previous signatures only after all views succeed and the secure write completes. Photos are transient; only 128-dimensional descriptors are stored in the device's Keychain. Appearance can be replaced or erased, and foreground recognition can be disabled.

When enabled, returning to the foreground hides the previous account, loads the local model, then activates AVFoundation for at most five seconds. Three consistent observations choose a candidate. Unknown, multiple or ambiguous faces retain manual selection. Automatic recognition never asks for camera permission; permission is requested only while the user enrolls. Cancellation, backgrounding, closing the window, timeout and inference failure release the capture session and erase transient images. A configured PIN is still required.

The interaction takes inspiration from [Cornelius](https://github.com/lfpoulain/Cornelius), whose code is not copied. This implementation uses independently integrated MIT face-api.js models with local CPU inference in an isolated, nonpersistent WebKit view. Camera images cannot trigger external network requests. Build and preview preparation include verified model assets and their notices in `Resources/FaceRecognition`; downloads use immutable revisions and SHA-256 checks. See `packaging/macos/face-recognition/NOTICE.md` and its manifest for provenance.

Validation on macOS: `node --test scripts/provider-host/macos-cloud-accounts.test.mjs scripts/provider-host/macos-face-recognition.test.mjs`. Harnesses cover migration, token rotation races, removal, PIN and persistent throttling, identity expiry and input reset, transactional appearance storage, descriptor ambiguity, temporal votes and actual offline WebKit model loading against a no-face image. They never activate the physical camera. Real recognition quality, camera permissions and camera indicator behavior require an opted-in run on the target Mac. Model distances are similarity heuristics, not a liveness check or a replacement for OS authentication.
